# 参考观察 → 设计原则 → Demo 证据

这份表是本项目最重要的“翻译层”：

> 参考页面看到了什么，不等于以后要复制什么。
> 先把观察翻译成设计原则，再用 Demo 展示原则如何落地。

Codex 使用本项目时，应优先读取“设计原则”和“迁移规则”，不要把 Demo 的页面结构当成目标产品的需求。

| 参考观察 | 抽象后的设计原则 | Demo 中的证据 | 迁移到新产品时 | 不要复制 |
|---|---|---|---|---|
| 侧栏按“概览、自动化、资源、控制面板”分组 | 导航按用户意图分组，而不是按代码模块分组 | `#drawer`、`[data-design-role="intent-navigation"]` | 根据新产品的真实任务重新命名和分组 | 原页面的路由树、产品名称、菜单文案 |
| 顶部有当前位置、搜索、主题和刷新 | 全局壳层应提供位置感、快速入口和环境控制 | `.topbar`、`.page-header` | 保留最必要的全局动作，避免把所有动作塞进顶栏 | 原页面的快捷键、品牌图标、固定尺寸 |
| 页面顶部先给标题、用途和数据新鲜度 | 用户先确认“我在哪里、这里解决什么、数据是否可信” | `[data-design-role="page-header"]` | 每个页面只写一个明确任务句，并在数据易变时显示更新时间 | 原页面的标题和英文眉题 |
| 指标区紧跟页面头部 | 首屏先给结论，再给证据和操作 | `[data-design-role="metric-group"]` | 只放真正影响当前决策的 2–4 个指标 | 原页面的数字、单位、指标数量 |
| 趋势图和连接状态并排 | 把“方向”和“当前可用性”放在同一决策区域 | `[data-design-role="health-evidence-grid"]` | 主任务需要时才使用双栏；窄屏改为顺序堆叠 | 原页面的 658/320 比例和具体数据 |
| 任务、动态、正在播放并列 | 把正在发生的工作、刚发生的证据和当前上下文放在一起 | `[data-design-role="live-work-grid"]` | 按新产品的主工作流选择列表、动态或预览，不强行三栏 | 原页面的媒体业务模块 |
| 系统资源、统计、排行、下载、最近入库继续向下展开 | 详情按“当前工作 → 证据 → 结果”递进，而不是首屏堆满 | `[data-design-role="supporting-evidence-grid"]`、`[data-design-role="output-grid"]`、`[data-design-role="media-output-grid"]` | 只保留能帮助判断、恢复或继续操作的支撑模块 | 完整复制参考页的长页面顺序 |
| 状态都带文字、颜色、进度或时间 | 状态必须回答“是什么、现在怎样、下一步是什么” | `.status-tile`、`.queue`、`.feed`、`.progress` | 为每个数据区域定义 fresh/loading/empty/error/retry 等状态 | 只用绿点、只用颜色或只用 Toast |
| 设置页把测试和保存分开 | 外部依赖的验证动作和持久化动作是两个不同决定 | `data-view="settings"`、`.form` | 让测试结果靠近字段，让保存状态可见，并保留恢复路径 | 原页面的配置项和敏感字段 |
| 移动端抽屉、单列、浮动入口避让内容 | 移动端是任务顺序重排，不是桌面端缩小 | `@media` 规则、`#menuToggle`、`.standalone-launcher` | 先保留标题和主动作，再放指标与支持内容；检查遮挡 | 原页面的断点和具体浮层位置 |

## 读表方式

### 如果你要做一个新产品

1. 从“抽象后的设计原则”挑选需要的维度。
2. 在“迁移到新产品时”写出新产品自己的页面和任务。
3. 对照“不要复制”检查品牌、路由、数据和页面骨架是否仍然来自参考。
4. 再打开 Demo，观察这个原则的视觉密度、间距、状态和响应式表现。

### 如果你要组合多个 UI 语言项目

每个维度只能有一个明确来源，例如：

```text
主语言：本项目的 shell、状态语义、运维密度
媒体卡片：另一个 UI 语言项目
图表：第三个 UI 语言项目
动效：第四个 UI 语言项目
```

不要把多个项目的颜色、圆角、阴影和间距混成一套“平均风格”。
